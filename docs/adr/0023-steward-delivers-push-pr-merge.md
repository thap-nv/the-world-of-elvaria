# ADR 0023 · The Steward delivers: push the quest branch, open a pull request, merge when checks are green

- Status: accepted · 2026-11-10
- Related: [implementation-plan.md](../implementation-plan.md) §3.16.7, §9.1 items 11 and 34; [product plan 0.8](../ke-hoach-dung-elvaria-0.8.md) §7, §14; [ADR 0005](0005-single-writer-steward-inbox.md), [ADR 0013](0013-treasury-and-redaction.md)
- Amends: [ADR 0012](0012-worktree-for-every-git-quest.md) (its "no automatic merge and no `git push`" was a stage-1 rule)

## Context

In stage 1 the owner merged by hand after the royal seal. In practice the owner handed that chore to a control session: push each sealed branch, open a pull request with the delivery letter as its body, wait for CI, merge ([phase-1 report](../guides/phase-1-report.md) §3). It is the largest recurring owner chore that needs no judgement. On 2026-11-10 the owner decided that Elvaria pushes quest branches, opens pull requests with the owner's git credential and merges.

## Decision

- Delivery is the Steward's work, never a character's. Every character session keeps `git push` denied (the fence of ADR 0007 does not change), and so does a judge's scratch plot (ADR 0022).
- `territory.delivery.mode` is `manual` (the default, stage-1 behaviour), `pr` (push and open the pull request) or `pr_merge`. The owner turns it on per territory.
- Order: verdict pass → royal seal when the quest needs one (`seal_default` of its kind, a claim above the character's level, `protected_paths`, the kingdom's `delegation`) → the territory's merge queue → update the quest branch by merging the base branch, never by rebasing → resolve `shared_paths` by their declared rule → rerun the checks → push `quest/<id>` → open the pull request → wait for `required_checks` → merge with the territory's `merge_method` (default: a merge commit) → `delivery.merged`.
- The Steward pushes only `quest/<id>` branches: no force push, no push to the base branch. (Amended 2026-11-27, CM-07/CM-08a, ADR 0032: it also pushes the `train/<territory>/<id>` branches it builds for a `deferred` territory, merges each by one pull request with a merge commit (a train needs `merge_method: merge`) and deletes it after the merge or when the train stops; and it merges a guest's pull request it did not open, on the owner's `enqueue_branch`, never writing to its branch.)
- The forge is a port (`Forge`: open, status, merge) with GitHub REST as its first implementation. The token comes from `git credential fill` each time it is needed, lives only in the Steward process, passes `redact`, and never reaches a prompt, a journal, an event or a character's env.
- Failures do not loop. A conflict the declared rules cannot resolve opens a merge quest for a knight, judged like any quest; red CI returns the quest with the log; a forge error or a CI timeout emits `delivery.failed` and goes to the owner's digest.
- (Amended 2026-11-13, owner's decision, PS-08) After `delivery.merged` the Steward deletes the remote `quest/<id>` branch it pushed, and no other. Before a push it scans the branch's diff with the redaction patterns (ADR 0013) and does not push on a hit.
- (Amended 2026-11-13, owner's decision, PS-08b) The owner may delegate the seal. A quest inside the seal part of `kingdom.delegation` (rank, kind, a territory in `pr_merge`) is created without `seal_required`, and the machine only ever raises it again: protected paths, a claim above the level, files outside the scope, a diff above the cap, a judge of a doer's family, an objection. No class seals or merges, and the `seal` command stays the owner's. One escaped defect of such a quest suspends the delegation for its territory until the owner re-arms it.
- (Amended 2026-11-17, PS-08d: (D) and (G) of the PS-08 plan, owner's decision 2026-11-15) The scan blocks a push on a treasury value or on one of redact's own-shape patterns; the three shared patterns (bearer token, credentials in a URL, secret assignment) only name their files in the `warnings` of `delivery.pushed`. Under `pr_merge` only a quest with the royal seal is merged (`mergeDue`); one done without it stops at its pull request until PS-08b. Red forge checks leave the quest `done` with `delivery.failed` (`checks_red`): returning it is PS-08f. Under every mode, a done quest whose branch reached the base branch is archived by the Steward, which then releases its plot.
- (Amended 2026-11-18, PS-08b: K9, K10 of the merge queue plan) The seal part is `kingdom.delegation.seal` (`max_rank`, `kinds`, `max_diff_lines`, 400 by default). A command that says `seal_required`, either way, wins; the owner's later edit of it ends the delegation, and a quest done without the seal outside it (`--no-seal`, a kind that does not seal) still stops at its pull request: `mergeDue` merges an unsealed quest only while the delegation covers it (`mayMergeUnsealed`). Besides the reasons above, the machine raises the seal when the machine judged alone, the rank is now above `max_rank`, the delegation no longer covers the quest, or its territory is suspended; the reasons are kept in `seal_raised`, set through `Move.before`, the transition table unchanged. Each merge without the seal is an item of the next digest with the `git revert` line the owner runs and pushes. The suspension itself (signals, re-arming) is PS-08g.
- (Amended 2026-11-18, PS-08g: K11 of the merge queue plan) An escape is one of two signals: a check of the base branch the patrol finds turned red while the merges since its last green patrol hold one without the seal, or the owner's `elvaria quest escaped <id>` (`report_escape`, `quest.escaped`) on a quest merged without it; the same report on a sealed quest only counts in the metrics. The Steward writes `delegation.suspended` once per suspension and rings; the suspension is derived from that line and `delegation.resumed` alone (`sealSuspendedOf`), so a restart keeps it, and no file holds it. The owner re-arms a territory with `elvaria territory delegation <id> --resume` (`resume_delegation`). A red forge check as a third signal waits for PS-08f.
- (Amended 2026-11-17, fix/push-scan, owner's decision (212)) A push sends every commit of `base..HEAD`, so the scan reads each commit's added lines as well as the branch's whole diff (a merge's own lines through `--remerge-diff`): a secret one commit adds and a later one removes still blocks the push, and `delivery.failed` names the commits that add it.
- (Amended 2026-11-23, CM-05, [ADR 0033](0033-late-machine-verdict.md)) A quest returned by a red check leaves `done` by a late machine verdict: `verdicts/<quest>-<n>-late.json` and the Steward's `done` + `verdict_fail` rows (to `returned`, to `open` for the machine's merge, to the infirmary once out of attempts), not two `return` rows; the seal and the delivery stamp go with it, so the rework is sealed again when the quest needs it and delivered again.

- (Amended 2026-11-25, RC-02: a push names the commit the Steward's checks passed on in `ELVARIA_CHECKED_HEAD`, when that run had a check and set none aside; the hooks still run.)
- (Amended 2026-11-26, RC-05, [ADR 0035](0035-checks-once-per-tree.md): where the queue would merge the base branch, it is merged before the checks after a session and kept only when they are green; the queue's update then merges only what moved since.)

## Alternatives

- Push and open the pull request only, the owner merges (the session's recommendation): it keeps the owner in every delivery. It stays available as mode `pr`.
- Let the character push: it breaks the fence and puts a credential within a model's reach.
- (Amended 2026-11-21, SEC-02: threat model A5, V2) Every git of the Steward (plots, deliveries, `credential fill`) runs after the `-c` switches of runner-core's `gitGuard`, read from `git config --list --show-scope` in the same folder just before the call (once per folder for a plot's git): `core.fsmonitor=false`, an empty `core.askPass`, the owner's `core.sshCommand` of system or global config (else `ssh`), and the owner's credential helpers alone, so no program that the territory's own config names runs and the token reaches none. `credential fill` still runs in the territory's folder, as the push does. The territory's hooks still run.

## Consequences

- The Steward gains network access to one host per forge; tests use a fake forge and a real git repository.
- A wrong merge is a merge commit and can be reverted; a quest that touches protected paths always waits for the seal ([ADR 0026](0026-guarded-self-change.md)).
- Pushes and merges are made under the owner's account; the event log records which quest caused each.
